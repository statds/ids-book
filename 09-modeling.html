9  Modeling

Predictive modeling uses information available at a defined time to estimate an outcome that is not yet known. This chapter asks whether fields available when an illegal-parking request is created can help identify requests that will remain open for at least one hour. We compare request detail and borough with area context from the Census-linked table:

  • population density;
  • household vehicle availability; and
  • median household income.

The analysis uses the same one-week, request-level data as earlier chapters. It predicts recorded closure time; it does not show that area characteristics cause a request to take longer or establish how predictions would perform in a different week.

The one-hour outcome connects the modeling question to the operational concern that illegal-parking reports may call for timely handling. It is an analytical cutoff, not a documented agency response standard. In the available week, 34.6% of requests with usable closure times were closed in under an hour, while 65.4% remained open for at least an hour. Recorded closure time is only a proxy for handling time: it may include dispatch, travel, queueing, reporting, and administrative steps. The analysis can predict this recorded outcome from observed fields, but it cannot isolate those processes.

9.1 Frame the Prediction

Before fitting a model, specify what it will predict and what information it can use:

  • Unit: one illegal-parking request from the distributed week.
  • Target: one if recorded closure time is at least one hour, and zero otherwise. Requests without a closure time cannot be labeled and are excluded.
  • Prediction time: request creation. Closure time and later processing fields are unavailable then and must not be predictors.
  • Request features: problem detail and borough, recorded when the request is created.
  • Area features: population density, median household income, and the estimated share of households with a vehicle, linked through the ZIP label (U.S. Census Bureau, 2024a, 2024b).

The one-hour cutoff is a modeling choice, not a documented agency standard. The density measure divides ACS population by 2024 Gazetteer ZCTA land area; the vehicle share is one minus the estimated fraction of households with no vehicle. These describe area context, not curb capacity or individual behavior. The ACS estimates cover 2020–2024, precede the request week, and have sampling uncertainty. We do not calculate the vehicle share’s uncertainty from the published margins of error.

The ZIP label links a request to a ZIP Code Tabulation Area (ZCTA), but the two geographies are related rather than identical, so this is an approximate match (U.S. Census Bureau, 2023, 2026). ZIP digits are labels, not quantitative predictors. A later benchmark uses the ZIP as a category to ask a different predictive question.

The prediction question is: among requests from this week, how well can the recorded fields distinguish requests that remain open for at least an hour? This is prediction within the observed setting. It is not a question about whether a predictor causes a longer closure, nor does it show performance in a future week. The four checks in Section 5.1 still apply: a model cannot repair an unclear target, an invalid measurement, an inadequate scope, or weak evidence.

9.2 Establish a Baseline

A baseline sets a reference that a more complex model must improve. Because about two-thirds of eligible requests meet the one-hour target, predicting the majority class for every request already gives roughly 65% accuracy. That result does not distinguish requests: it labels every case as taking at least an hour. Accuracy alone would therefore make a useless classifier look respectable.

The analysis starts from the shared preparation function rather than repeating the import and filtering workflow from Chapter 6. It links the requests to the Census context already documented in Section 6.4, reports unmatched and incomplete records, and defines the binary outcome. It does not alter the source request data or rebuild the Census lookup. The train-test split reserves one quarter of complete requests for a final evaluation. Stratification keeps the target proportion similar in the two sets; it does not make the records independent or simulate a future week.

from scripts.parking_requests import attach_zcta_context, load_parking_requests

The checks make the analysis population and target visible before any model is fitted. The lookup matches 13,033 of 13,040 requests; 58 matched requests lack at least one area measure, including nine requests with no household vehicle estimate because their ACS household denominator is zero. The complete-case analysis therefore uses 12,975 requests from 176 ZCTAs. The split contains 9,731 training requests and 3,244 test requests, with nearly identical target proportions. Fixing the random seed makes this example reproducible, while stratification controls only the class proportions. Requests from the same ZCTA can appear in both sets, so the test set evaluates new requests in areas represented during training rather than transfer to unfamiliar areas.

9.3 Use a GLM

A generalized linear model (GLM) relates a response distribution to a predictor through a link function. For a binary outcome, the response is modeled with a Bernoulli distribution and a logit link; this special case is logistic regression. GLMs also include familiar linear regression with a Gaussian response and identity link, as well as count models with a Poisson response and log link. The response distribution and link should follow the outcome’s scale and support, rather than being selected only because a software function is familiar (McCullagh & Nelder, 1989; Nelder & Wedderburn, 1972).

For request \(i\), let \(Y_i=1\) indicate that closure takes at least one hour, and let \(p_i = \Pr(Y_i=1 \mid \mathbf{x}_i)\). Logistic regression models the log odds as a linear combination of predictors:

\[ \log\!\left(\frac{p_i}{1-p_i}\right) = \beta_0 + \beta_1 x_{i1} + \cdots + \beta_k x_{ik}. \]

The inverse-logit transformation maps any real-valued linear predictor to a probability between zero and one. Odds compare the probability of an event with the probability it does not occur. For example, a probability of 0.75 corresponds to odds of \(0.75/0.25=3\) to 1, while a probability of 0.5 corresponds to odds of 1 to 1. A coefficient describes a change in log odds, holding the other included predictors fixed; exponentiating it gives an odds ratio. An odds ratio is not a probability difference and does not by itself describe a causal effect.

The first GLM includes problem detail, borough, population density, median household income, and household vehicle availability. The three area measures are standardized across training requests, so their odds ratios describe a one-standard-deviation difference in the request-weighted feature values. The formula interface compares each categorical level with a reference category and holds the other predictors fixed. These coefficients describe conditional associations in the fitted model, not changes caused by the area characteristics (statsmodels Developers, 2026).

import numpy as np
import statsmodels.api as sm
import statsmodels.formula.api as smf

glm_data = X_train.copy()
glm_data["long_closure"] = y_train
glm_formula = (
    "long_closure ~ C(problem_detail) + C(borough) + "
    "standardize(population_density_per_sqmi) + "
    "standardize(median_household_income) + "
    "standardize(share_households_with_vehicle)"
)
glm_fit = smf.glm(
    glm_formula,
    data=glm_data,
    family=sm.families.Binomial(),
).fit()

population_density_log_odds = glm_fit.params[
    "standardize(population_density_per_sqmi)"
]
income_log_odds = glm_fit.params["standardize(median_household_income)"]
vehicle_share_log_odds = glm_fit.params[
    "standardize(share_households_with_vehicle)"
]
pd.Series({
    "Population-density odds ratio per standard deviation": np.exp(
        population_density_log_odds
    ),
    "Income odds ratio per standard deviation": np.exp(income_log_odds),
    "Household vehicle-share odds ratio per standard deviation": np.exp(
        vehicle_share_log_odds
    ),
})

Each displayed odds ratio compares requests that differ by one training-set standard deviation in the corresponding area measure, while the other model features are held fixed. For example, an odds ratio above one indicates higher fitted odds of a one-hour closure for a one-standard-deviation increase; it does not say how many percentage points the probability rises. The context values repeat across requests in the same ZCTA, so area patterns are supported by 176 distinct ZCTAs, not by treating each request as an independent area. These are conditional associations, not individual-level effects or causal estimates. They also rely on a linear relationship between each standardized area measure and log odds.

9.4 Check the Model

Model checks ask whether the chosen specification represents the observed relationships adequately. They differ from test-set evaluation: a model can fit the training records poorly, or fit them closely while predicting new records poorly. Logistic regression does not assume normally distributed errors or constant error variance as ordinary least squares does. Its assumptions instead concern the conditional Bernoulli response and the specified relationship between predictors and log odds. Residual and influence diagnostics can reveal unusual records or lack of fit, but no single diagnostic proves that a model is correct (Hosmer et al., 2013; Pregibon, 1981).

The current model makes several assumptions that can be checked only in part:

  • Each standardized area measure has a linear relationship with log odds.
  • The model is additive, so the detail contrast is the same across boroughs unless an interaction is included.
  • Sparse categories may produce unstable estimates.
  • Repeated Census values mean that area-level patterns are supported by 176 distinct ZCTAs rather than by the full request count.

Compare observed outcome rates with mean fitted probabilities across boroughs and across ordered groups of each continuous predictor, retaining the count in each group. Calibration is one check: predictions near 0.7 should correspond to an observed outcome rate near 0.7 among comparable requests (Calster et al., 2019).

The training-set summary below compares observed target rates with average fitted probabilities by borough. A large discrepancy can flag a lack of fit for a group, while close averages do not rule out errors for individual requests or interactions hidden within a borough. This is an in-sample check for the simple GLM, not an estimate of future prediction accuracy.

9.5 Evaluate Predictions

Evaluation asks how well the fitted model predicts requests it did not use for estimation or tuning. A training score is optimistic because the model has already adapted to those records. The reserved test set is used only after model choice; repeatedly adjusting a model after inspecting its test performance turns that set into another training resource and weakens the evaluation. Here, even a clean random holdout supports only a limited claim: it estimates performance for additional requests drawn under a similar one-week data-generating process.

Prediction metrics depend on the outcome’s scale. Numeric outcomes are evaluated by comparing predicted values with observed values; classification begins with class probabilities and applies a threshold to assign labels. The same train-test separation applies to both tasks, but their metrics answer different questions.

9.5.1 Numeric outcomes

For a numeric outcome, a residual is the observed value minus its prediction. Three common scores summarize different aspects of these residuals:

\[ \begin{aligned} \text{MAE} &= \frac{1}{n}\sum_{i=1}^{n}|y_i - \hat{y}_i|, \\ \text{RMSE} &= \sqrt{\frac{1}{n}\sum_{i=1}^{n}(y_i - \hat{y}_i)^2}, \\ R^2 &= 1 - \frac{\sum_{i=1}^{n}(y_i - \hat{y}_i)^2} {\sum_{i=1}^{n}(y_i - \bar{y})^2}. \end{aligned} \]

Mean absolute error (MAE) reports a typical miss in the outcome’s units. Root mean squared error (RMSE) uses the same units but gives large errors more influence because it squares them before averaging. The coefficient of determination, \(R^2\), compares squared prediction error with variation around the observed mean; a test-set value can be negative when predictions are worse than that reference (scikit-learn Developers, 2026c).

Recorded closure hours are numeric, so the held-out records also allow us to compare simple duration baselines. The training mean is the constant prediction that minimizes squared error; the training median minimizes absolute error. This comparison shows how numeric prediction metrics work without introducing a second fitted model.

from sklearn.metrics import mean_absolute_error, mean_squared_error, r2_score

duration_train = model_data.loc[X_train.index, "closure_hours"]
duration_test = model_data.loc[X_test.index, "closure_hours"]
duration_scores = {}
for name, value in {
    "Training mean": duration_train.mean(),
    "Training median": duration_train.median(),
}.items():
    prediction = pd.Series(value, index=duration_test.index)
    duration_scores[name] = {
        "MAE (hours)": mean_absolute_error(duration_test, prediction),
        "RMSE (hours)": mean_squared_error(
            duration_test, prediction
        ) ** 0.5,
        "R-squared": r2_score(duration_test, prediction),
    }
display(pd.DataFrame(duration_scores).T)

The training-median baseline has lower MAE (2.67 hours) than the training-mean baseline (3.16 hours), while the mean baseline has lower RMSE (4.96 hours versus 5.25 hours). The right-skewed closure-time distribution lets a few long closures have a large effect on RMSE. Both \(R^2\) values are near zero or negative, so these constant forecasts capture little of the test-set variation. They provide reference errors, not an evaluation of a feature-based regression model.

9.5.2 Binary outcomes

For binary classification, a model often estimates a probability and then uses a threshold to assign one of two labels. The positive class is the category of interest, and changing the threshold changes the predicted labels and the resulting threshold-based scores.

9.5.3 Confusion matrix

A confusion matrix compares observed classes with the classes predicted at a chosen threshold. Its four cells count correct and incorrect classifications. A true positive (TP) is an actual positive predicted as positive; a false negative (FN) is an actual positive predicted as negative. A false positive (FP) is an actual negative predicted as positive; a true negative (TN) is an actual negative predicted as negative. Rows below are actual classes and columns are predicted classes, matching the convention used by scikit-learn (scikit-learn Developers, 2026c).

In this chapter’s parking analysis, a positive is a request that remains open for at least one hour, and a negative closes sooner. The illustrative threshold is 0.5, so predicted probabilities at or above 0.5 are classified as positive. The displayed test-set counts use this rule and the layout in Table 9.1.

Each metric uses a different margin or combination of cells. The numerator and denominator make clear which errors a score counts:

Quantity Common names Definition
True positive rate TPR, sensitivity, recall, hit rate, probability of detection \(TP/(TP+FN)\): fraction of actual positives flagged
False negative rate FNR, miss rate \(FN/(TP+FN)\): fraction of actual positives missed
True negative rate TNR, specificity, selectivity \(TN/(TN+FP)\): fraction of actual negatives not flagged
False positive rate FPR, fall-out, false alarm rate \(FP/(TN+FP)\): fraction of actual negatives flagged
Positive predictive value PPV, precision \(TP/(TP+FP)\): fraction of flagged requests that are positive
False discovery rate FDR \(FP/(TP+FP)\): fraction of flagged requests that are negative
Negative predictive value NPV \(TN/(TN+FN)\): fraction of unflagged requests that are negative
False omission rate FOR \(FN/(TN+FN)\): fraction of unflagged requests that are positive
Accuracy Overall accuracy, correct classification rate \((TP+TN)/(TP+TN+FP+FN)\)
F1 score F1 measure, F-score with \(\beta=1\) \(2\,\mathrm{Precision}\,\mathrm{Recall}/(\mathrm{Precision}+\mathrm{Recall})\)

Different fields use different names for several of the same ratios:

  • TPR, sensitivity, and recall all divide true positives by actual positives. They ask what fraction of requests that remained open at least an hour the model flagged.
  • PPV and precision divide true positives by predicted positives. They ask what fraction of flagged requests remained open at least an hour.
  • Specificity and TNR measure the fraction of actual negatives not flagged; FPR is the fraction of actual negatives that were flagged.
  • F1 is the harmonic mean of precision and recall. It does not account for true negatives.

The complementary pairs TPR/FNR, TNR/FPR, PPV/FDR, and NPV/FOR each sum to one. The \(F_\beta\) score makes the precision-recall balance explicit:

\[ F_\beta = (1 + \beta^2) \frac{\mathrm{Precision}\,\mathrm{Recall}} {\beta^2\,\mathrm{Precision} + \mathrm{Recall}}. \]

The familiar F1 score sets \(\beta=1\). Values above one give more weight to recall, while values below one give more weight to precision; the choice should reflect the decision context rather than a universal preference (scikit-learn Developers, 2026c; Wikipedia contributors, n.d.).

Accuracy is the fraction of correct labels and can hide poor performance on one class when class frequencies differ. ROC AUC measures how well the model ranks positive cases above negative cases across thresholds; 0.5 indicates chance-level ranking and 1 indicates perfect ranking. AUC neither chooses a threshold nor checks whether probabilities are accurate. Log loss evaluates the probabilities themselves and penalizes confident errors. For observed binary outcomes \(y_i\) and predicted probabilities \(p_i\), it is

\[ -\frac{1}{n}\sum_{i=1}^{n} \left[y_i\log(p_i) + (1-y_i)\log(1-p_i)\right]. \]

These measures answer different questions and none is universally best (scikit-learn Developers, 2026c).

The threshold determines how missed long closures trade off against unnecessary alerts. The data do not specify the costs of these errors, so the example uses 0.5 only for illustration. A threshold selected for use would be chosen with training or validation data, then evaluated once on the held-out test set.

The baseline assigns every request the training-set target prevalence as its probability and predicts the majority class. The Census-context model one-hot encodes problem detail and borough, standardizes the three area measures, and fits logistic regression. The table compares their test metrics; classification measures use a 0.5 threshold. Since the positive class is more common, do not read accuracy alone. Compare it with ROC AUC, log loss, and the confusion matrix to see whether the model finds requests that close sooner or merely repeats the majority-class prediction.

from sklearn.dummy import DummyClassifier
from sklearn.metrics import (
    accuracy_score,
    confusion_matrix,
    f1_score,
    log_loss,
    precision_score,
    recall_score,
    roc_auc_score,
)
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

candidate_features = categorical_features + numeric_features
preprocessor = ColumnTransformer([
    ("categorical", OneHotEncoder(handle_unknown="ignore"), categorical_features),
    ("numeric", StandardScaler(), numeric_features),
])
baseline = DummyClassifier(strategy="prior").fit(
    X_train[candidate_features], y_train
)
baseline_probability = baseline.predict_proba(X_test[candidate_features])[:, 1]

model = make_pipeline(
    preprocessor,
    LogisticRegression(max_iter=3000),
)
model.fit(X_train[candidate_features], y_train)
test_probability = model.predict_proba(X_test[candidate_features])[:, 1]

def score_predictions(probability):
    predicted_class = probability >= 0.5
    return {
        "accuracy": accuracy_score(y_test, predicted_class),
        "ROC AUC": roc_auc_score(y_test, probability),
        "log loss": log_loss(y_test, probability),
        "TPR / recall": recall_score(y_test, predicted_class),
        "specificity": recall_score(y_test, predicted_class, pos_label=0),
        "precision": precision_score(y_test, predicted_class),
        "F1": f1_score(y_test, predicted_class),
    }

The ROC curve traces the true positive rate against the false positive rate as the probability threshold changes. In the table above, TPR is also called recall or sensitivity; FPR is one minus specificity. Each point represents a different threshold, so the curve displays the trade-off between finding more one-hour closures and incorrectly flagging requests that close sooner. The area under this curve is the ROC AUC reported in the score table.

from sklearn.metrics import roc_curve

This first comparison gives the model a common reference and an initial held-out score. Its results are not the final model-selection result because the regularization strength still needs to be chosen using training data alone. A 0.5 classification threshold is convenient for illustration, not a universal decision rule. A real alerting system would set a threshold by considering the consequences of each kind of error with the people who would use the predictions.

9.6 Regularize Logistic Regression

The model has many coefficients because problem detail and borough are one-hot encoded, and the later ZIP-label model adds a coefficient for each observed area. Some categories are sparse, while the Census measures can be correlated. An unpenalized fit can assign unstable, large coefficients to these patterns and perform worse on new requests. Regularization limits coefficient size to trade a small amount of training fit for more stable predictions.

Logistic regression estimates coefficients by maximizing the Bernoulli log-likelihood. A penalty adds a cost for large coefficients:

\[ \widehat{\boldsymbol{\beta}}_\lambda = \arg\min_{\boldsymbol{\beta}} \left\{ -\sum_{i=1}^{n} \left[y_i\log(p_i) + (1-y_i)\log(1-p_i)\right] + \lambda P(\boldsymbol{\beta}) \right\}. \]

Here, \(p_i\) is the fitted probability for request \(i\), and the penalty does not include the intercept. The \(L_2\) penalty is \(P(\boldsymbol{\beta}) = \sum_{j=1}^{p}\beta_j^2\); it shrinks coefficients without usually setting them exactly to zero. The \(L_1\) penalty is \(P(\boldsymbol{\beta}) = \sum_{j=1}^{p}|\beta_j|\) and can set some coefficients to zero, producing a sparse model. Elastic net combines the two penalties (Tibshirani, 1996; Zou & Hastie, 2005). Since several Census measures may carry overlapping information, this example uses \(L_2\) regularization to stabilize the estimates without arbitrarily selecting one of a group of correlated predictors.

Scikit-learn’s logistic regression applies \(L_2\) regularization by default. Its C parameter is inversely related to the penalty strength, so smaller values apply stronger shrinkage (scikit-learn Developers, 2026b). Numeric predictors must be standardized because the penalty acts on coefficient size; otherwise, a change in measurement units changes how strongly a predictor is penalized. The analysis standardizes the area measures and keeps preprocessing inside the cross-validation pipeline.

Cross-validation selects C using training data alone. Within each fold, the pipeline learns its scaling, category encoding, and model coefficients from the fold’s training records, then evaluates log loss on its validation records. The candidate with the lowest mean validation log loss is refitted on the complete training set. The separate test set remains untouched until selection is complete because using the same cross-validation scores both to select and report final performance can be optimistic (scikit-learn Developers, 2026a; Varma & Simon, 2006).

The comparison separates measured area context from a postal-code lookup. All four models use the same training and test requests. One model uses problem detail and borough; a second adds three ACS-derived area measures; a third adds the incident ZIP label as a categorical identifier; and a fourth uses a smoothed target encoding of that label. Five-fold stratified cross-validation selects C by log loss, a probability-focused criterion. Standardization and one-hot encoding are inside the pipeline so each fold learns its preprocessing from its own training portion. The ZIP-label model is a predictive benchmark for areas already represented in the data; its coefficient for a ZIP label does not explain what neighborhood feature may relate to closure time.

One-hot encoding gives each ZIP label its own coefficient, which can be unstable when some labels have few requests. Smoothed target encoding offers another representation: it replaces a label with an estimate of its one-hour closure rate, then shrinks that estimate toward the overall rate. For ZCTA \(j\), a common estimate is

\[ \widetilde{p}_j = \frac{s_j + \alpha \bar{p}}{n_j + \alpha}, \]

where \(s_j\) is the number of one-hour closures in ZCTA \(j\), \(n_j\) is its number of requests, \(\bar{p}\) is the overall training-set rate, and \(\alpha\) controls shrinkage. Larger values of \(\alpha\) pull area estimates more strongly toward the overall rate. This empirical Bayes idea is useful for categories with different sample sizes (Micci-Barreca, 2001; Pargent et al., 2022). Since the encoding uses the outcome, fitting it on each row’s own outcome would leak information into the training data. The encoder below cross-fits the training values within each training fold; for the held-out test set, it uses category rates estimated from the full training set (scikit-learn Developers, 2026d).

def tune_logistic(categorical, numeric):
    transformers = []
    if categorical:

            "categorical",
            OneHotEncoder(handle_unknown="ignore"),
            categorical,

    )

For this split, adding the Census measures changes test ROC AUC from about 0.577 to 0.589 and log loss from 0.636 to 0.631. The improvement is modest, but it indicates that the supplied area attributes add some predictive information beyond problem detail and borough in this test design. The ZIP-label model scores higher, with ROC AUC about 0.690 and log loss 0.593. Because the same ZCTAs occur in training and test sets, this score reflects area-specific prediction for locations represented in training. It neither identifies a cause nor demonstrates transfer to a new ZCTA or a later week.

Smoothed target encoding gives a similar test ROC AUC of about 0.688 and log loss of 0.595, with the cross-validation procedure selecting a smoothing value of 10. Three test requests have ZIP labels absent from the training set; the encoder assigns those labels the overall training rate. This comparison shows that a compact, partially pooled encoding can retain much of the ZIP-specific predictive signal in this split. It does not establish that ZIP-level outcome rates will transfer to future requests, and its learned category values should not be interpreted as neighborhood causes.

The Census estimates offer a more interpretable area-level question than the ZIP label, but they do not measure the mechanisms that directly govern parking or request processing. Population density is residents per square mile, not curb or parking-space density. Household vehicle availability is not ownership, registration, vehicle activity, or parking location, and median household income does not describe an individual requester. These ACS measures repeat across requests in the same ZCTA and carry sampling uncertainty; the vehicle share’s uncertainty has not been propagated. Only 176 ZCTAs contribute independent area contexts in this analysis. Direct measures of curb regulations, parking supply, vehicle activity, or precinct workload would be more informative for those processes. Any resource- allocation use would also require a separate review of measurement, fairness, and consequences for affected neighborhoods.

Regularization controls model complexity but does not replace diagnosis. The selected penalty can stabilize estimates while leaving omitted variables, measurement error, unfair performance differences, and domain changes unresolved. Area-level predictors also require validation that respects their shared geography when the intended use concerns new areas. The model’s intended use and validation design must therefore be considered together.
