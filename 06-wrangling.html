6  Data Preparation

Data preparation constructs an analysis table from acquired records while preserving the evidence needed to evaluate each transformation. The input in this chapter is the distributed NYPD-directed 311 archive and the scope defined in Chapter 5. Its principal output is a request-level table with documented field names, derived closure hours, a creation-time category, and matched Census area context where a valid match exists. The domain, measurement, scope, and evidence checks in Section 5.1 determine which fields are retained and which operations require justification. A successful transformation need not make every value regular: an unmatched ZIP label or an unusual timestamp can be a finding about the source rather than a value to overwrite. The workflow therefore separates changes in representation from new analytical assumptions, checks that request identity and scope survive each stage, and records what remains uncertain before the prepared table is used for exploration or visualization.

6.1 From Source Records to an Analysis Table

Data preparation starts from a question and a retained source, not from an assumption that the downloaded table is already analysis-ready. The previous chapter established the observational unit, checked the requested time window, and selected illegal-parking requests. Here, those checks become input conditions for the preparation workflow: scope assertions detect a changed or incorrect input, while later checks verify that transformations preserve the intended records. The chapter then standardizes representations where the meaning is clear, derives variables needed for analysis, and considers geographic enrichment only when units and geographies align. The steps are iterative because a transformation can expose a problem or show that a question requires different data.

A preparation plan separates three classes of decisions because they have different implications for the resulting claim. Scope decisions select eligible observations and fields. Representation decisions encode a recorded value for reliable computation without changing its documented meaning, as when a ZIP Code is stored as text. Analytical decisions define new measurements or resolve uncertain values, as when a particular hour range is designated nighttime. Every class should leave an auditable record, but analytical choices especially require a rationale because they can change the outcome or comparison. The original ZIP archive remains unchanged. Chapter 5 demonstrated its acquisition and initial profile; the code below repeats only the import, timestamp parsing, and row filters needed for this chapter to run independently. Temporary Feather examples in that chapter do not provide an input here. Each subsequent stage creates a derived data frame and verifies the assumptions that its operation introduces.

from pathlib import Path

import pandas as pd

data_path = Path("data") / "311_nypd_lbdwk_2026.csv.zip"
requests = pd.read_csv(
    data_path,
    compression="zip",
    dtype={"Unique Key": "string", "Incident Zip": "string"},
    low_memory=False,
)

date_format = "%m/%d/%Y %I:%M:%S %p"
for column in ["Created Date", "Closed Date"]:
    requests[column] = pd.to_datetime(
        requests[column], format=date_format, errors="coerce"
    )

start = pd.Timestamp("2026-09-06")
end = pd.Timestamp("2026-09-13")
parking = requests.loc[
    requests["Created Date"].between(start, end, inclusive="left")
    & requests["Problem (formerly Complaint Type)"].eq("Illegal Parking")
].copy()

The import block reconstructs the intended analysis scope without overwriting the downloaded archive. The half-open timestamp interval includes requests created on every day of the selected week and excludes those returned from the following Sunday; the problem condition restricts the subset to illegal-parking requests. The observational unit remains one service request, so a row restriction changes the eligible population but does not aggregate or validate individual observations. The explicit datetime format also exposes parsing failures as missing timestamps, which must be checked rather than silently interpreted as absent service activity. The resulting frame can still contain missing fields, unexpected category values, duplicate identifiers, or disagreements among geographic descriptors. Those issues require separate diagnostics before a derived variable or merge can be trusted. The subset also remains limited to NYPD-directed requests from one week, regardless of how consistently its columns are represented.

6.2 Recheck Scope Before Transforming

The compact scope report tests the conditions on which this preparation workflow depends. Section 5.4 documented the delivered extract’s agency, timestamp, identifier, and missingness patterns; reproducing those diagnostic tables would add little to a chapter about transformation. The present check instead treats the expected row unit and filters as executable invariants: identifiers must be present and unique, creation times must fall within the selected half-open week, and every retained row must carry the illegal-parking problem label. These tests serve a different purpose from the initial profile. They detect a changed input file, an altered filter, or a parsing failure before derived columns are constructed. A failed invariant should prompt inspection of the source and the preparation code; it should not be repaired by automatically dropping records until the check passes. This chapter remains independently executable while the substantive diagnosis stays in the formulation chapter.

scope_checks = pd.Series({
    "rows": len(parking),
    "no missing request identifiers": not parking["Unique Key"].isna().any(),
    "unique request identifiers": parking["Unique Key"].is_unique,
    "all in intended week": parking["Created Date"].between(
        start, end, inclusive="left"
    ).all(),
    "all illegal parking": parking[
        "Problem (formerly Complaint Type)"
    ].eq("Illegal Parking").all(),
}, name="passed")

The invariant report confirms that the selected requests and their identifiers remain intact before transformations. Coordinate completeness is not a condition for the ZIP-label merge below, because that operation uses the provider’s Incident Zip field rather than latitude and longitude. Removing requests without coordinates at this stage would therefore change the population for a reason unrelated to the planned join. A subsequent point map or distance calculation has a different eligibility rule and must report the resulting exclusions separately. An area match also cannot restore a missing point location: an area label identifies a region, while distance to a precinct requires a location and a specified distance metric. These examples illustrate why eligibility should be defined for each analytical quantity instead of imposed once as a generic complete-case filter.

6.3 Standardize Representations Conservatively

Representation changes make fields usable without asserting new facts about the observations. Dates should use datetime types, while ZIP Codes and request keys should remain strings because their digits are labels rather than measured magnitudes. Converting a ZIP Code such as 00501 to an integer would remove its leading zero; recoding a blank, N/A, and Unspecified to one missing value would be justified only if their documented meanings coincide. Column names require the same care. The NYC export uses spaces, punctuation, capitalization, and historical parenthetical wording; these labels are valid but inconvenient for repeated analysis. A derived table can use consistent names while the imported source and a complete source-to-analysis mapping retain the provider’s terminology. The mapping must be checked for collisions because two distinct source fields can normalize to the same string. A collision requires explicit disambiguation before either field is renamed.

Category standardization requires evidence about the meanings of values, not only a preference for uniform text. The frequency table in Section 5.7 established which problem details motivate the working comparison. The following code inspects the distinct source strings before any recoding. The observed leading labels are interpretable, and apparent similarity between two labels would not by itself establish that they describe the same reporting condition. A data dictionary or curator explanation would be needed before combining categories with different names. By contrast, the code below changes column names to make operations easier while leaving category values unchanged. Keeping those two decisions separate preserves the provider’s distinctions and allows later readers to evaluate a proposed recode against the source.

detail_column = "Problem Detail (formerly Descriptor)"
observed_details = (
    parking[detail_column]
    .dropna()
    .drop_duplicates()
    .sort_values()
    .reset_index(drop=True)
    .rename("observed detail")
    .to_frame()
)

The short display confirms that the derived table exposes analytical names while retaining the provider’s values. The mapping table above records the correspondence between the two schemas; it should accompany any exported analysis table so that a future reader can trace a variable back to its source. This distinction matters when a provider changes a label but not a definition, or retains a label while changing how a field is populated. Neither case can be resolved from normalized column names alone. A later comparison across agencies or years would require a data-dictionary review of field definitions and collection rules in addition to consistent code syntax. Thus, standardization improves the reliability of operations on the table without claiming that all similarly named values are measured in the same way.

6.4 Derive Variables from Documented Meanings

Derived variables translate recorded fields into measurements required by the question while making new assumptions explicit. Let \(C_i\) and \(L_i\) denote the recorded creation and closure timestamps for request \(i\). The derived value \(T_i=(L_i-C_i)/3600\) is the elapsed interval in hours when the timestamp difference is measured in seconds and both times are available. Its validity requires successful parsing and a nonnegative chronology. The definition does not assert that an officer arrived at \(L_i\) or that the reported condition ended then; those are distinct events that the archive does not measure. Keeping the two timestamps alongside \(T_i\) permits an analyst to inspect a surprising value or revise the definition. A variable name such as closure_hours communicates the measurement more accurately than a label that would imply field response. The following calculation checks the resulting field before it is used as an outcome.

analysis["closure_hours"] = (
    analysis["closed_at"] - analysis["created_at"]
).dt.total_seconds() / 3600

duration_check = pd.Series({
    "missing": analysis["closure_hours"].isna().sum(),
    "negative": analysis["closure_hours"].lt(0).sum(),
    "median": analysis["closure_hours"].median(),
    "maximum": analysis["closure_hours"].max(),
}, name="value")
duration_check.to_frame()

The duration check distinguishes missing outcomes, impossible chronology, and unusually long but nonnegative intervals. A negative value contradicts the expected order of creation and closure if both timestamps refer to the same request timeline; its source should be inspected before exclusion because parsing or a later correction may explain it. A missing closure timestamp leaves the interval undefined, and substituting the observation date would invent a closure event. A large positive interval is not automatically erroneous because administrative closure may occur well after a report is made. The median and maximum in the report serve different diagnostic purposes: one characterizes the center, while the other prompts inspection of the upper tail. Chapter 7 examines that distribution rather than imposing an arbitrary cutoff during preparation.

Time-of-day groups require a boundary that reflects the intended comparison. “Night” has no universal definition, so the example assigns requests created from 8 p.m. through 5:59 a.m. to nighttime and those from 6 a.m. through 7:59 p.m. to daytime. The code leaves a missing creation hour unclassified instead of treating it as daytime. This categorical field can support a simple comparison, but it compresses variation across hours and ignores differences among individual dates, including the holiday in the selected week. The original timestamp remains in the table so that an analyst can examine hourly patterns or repeat the comparison under a different boundary. If the substantive question concerns staffing or reporting conditions, the boundary should be justified with relevant domain information rather than adopted solely because the resulting groups have convenient sizes.

hour = analysis["created_at"].dt.hour
analysis["time_period"] = pd.Series(
    pd.NA, index=analysis.index, dtype="string"
)
analysis.loc[hour.between(6, 19), "time_period"] = "day"
analysis.loc[hour.ge(20) | hour.lt(6), "time_period"] = "night"

6.5 Merge Area-Level Context with Checks

An area-level merge attaches contextual measurements to request records only under an explicit geographic matching rule. The request table has one row per service request; the Census context table has one row per ZIP Code Tabulation Area (ZCTA). The provider’s Incident Zip is a postal ZIP Code label, whereas a ZCTA is a Census statistical area derived from address patterns. Equal five-digit strings permit a lookup but do not make the geographies identical, and some postal ZIP Codes have no corresponding ZCTA (U.S. Census Bureau, 2023). The intended join is many requests to one context row, so a duplicate key on the right would incorrectly multiply requests. The reference period of the attached estimate also matters: a value measured before the request week describes earlier area context, not a contemporaneous attribute of an individual report. These conditions must be stated before the software merge is interpreted as evidence about place.

The supplied data/zcta_context.csv contains the 221 ZCTAs in NYC Open Data’s city list and their 2024 American Community Survey (ACS) five-year population and median household income estimates (NYC Open Data, 2026; U.S. Census Bureau, 2026). It also records margins of error, an income top-coding indicator, and the estimate year. The provenance and conversion rules in data/zcta_context.md distinguish the Census estimates from the NYC boundary list used to select areas. These fields allow an analyst to check both the statistical meaning of an attached value and the geographic coverage of the lookup. The code verifies that each context key is a five-digit string, occurs once, and has the expected reference year before the merge. It then retains unmatched requests and reports them separately. The result is a documented link between labels, not an assertion that a postal area and its similarly named ZCTA have identical boundaries.

The NYC ZCTA selection comes from the zcta5 column of the city’s published dataset, as the following acquisition code shows. The chapter uses the saved CSV during rendering so that a live web request cannot change its results. The complete extraction, including both ACS tables, is in scripts/build_zcta_context.py.

from io import StringIO

import requests

zcta_source = "https://data.cityofnewyork.us/resource/35j5-n34v.csv"
response = requests.get(
    zcta_source,
    params={"$select": "zcta5", "$limit": 5000},
    timeout=60,
)
response.raise_for_status()
city_zctas = pd.read_csv(
    StringIO(response.text), dtype={"zcta5": "string"}
)["zcta5"].drop_duplicates()
len(city_zctas)
zcta_context = pd.read_csv(
    Path("data") / "zcta_context.csv",
    dtype={"zcta": "string"},
)
zcta_context["zcta"] = zcta_context["zcta"].str.strip()

if zcta_context["zcta"].isna().any():
    raise ValueError("The ZCTA lookup contains missing keys.")
if not zcta_context["zcta"].str.fullmatch(r"\d{5}").all():
    raise ValueError("ZCTA keys must be five-digit strings.")
if zcta_context["zcta"].duplicated().any():
    raise ValueError("The ZCTA lookup must contain one row per key.")
if not zcta_context["acs_year"].eq(2024).all():
    raise ValueError("The ZCTA lookup contains an unexpected ACS year.")

# Match only syntactically five-digit request ZIP values. Do not silently
# pad or otherwise repair values that fail this check.
incident_zip = analysis["incident_zip"].str.strip()
analysis["zcta_match"] = incident_zip.where(
    incident_zip.str.fullmatch(r"\d{5}", na=False)
)

contextual_analysis = analysis.merge(
    zcta_context,
    how="left",
    left_on="zcta_match",
    right_on="zcta",
    validate="many_to_one",
    indicator="zcta_match_status",
)

if len(contextual_analysis) != len(analysis):
    raise ValueError("The area-level join changed the request count.")
if not contextual_analysis["request_id"].is_unique:
    raise ValueError("The area-level join duplicated request identifiers.")

join_report = pd.Series({
    "requests": len(contextual_analysis),
    "matched requests": contextual_analysis[
        "zcta_match_status"
    ].eq("both").sum(),
    "unmatched requests": contextual_analysis[
        "zcta_match_status"
    ].eq("left_only").sum(),
    "distinct unmatched ZIP values": contextual_analysis.loc[
        contextual_analysis["zcta_match_status"].eq("left_only"),
        "incident_zip",
    ].nunique(dropna=False),
}, name="count")
join_report.to_frame()

The validate argument turns the assumed join cardinality into an executable check. If a lookup key is duplicated, the join can multiply request rows and inflate subsequent counts. The left join preserves requests that lack a match, and its indicator distinguishes matched from unmatched rows. Unmatched values should be examined for missing identifiers, non-ZCTA ZIP Codes, formatting differences, boundary mismatch, or a flawed lookup; they should not be silently dropped or repaired by adding leading zeros without evidence. In this extract, 13,033 of 13,040 illegal-parking requests match a listed ZCTA; the seven unmatched requests remain in the table for other analyses.

Area context permits new comparisons only after the target quantity has been specified at the appropriate unit. A ZCTA population estimate can serve as the denominator of requests per resident during the observation week, but the numerator counts reports rather than verified conditions and the denominator does not measure curb space or vehicle exposure. Income and other area characteristics can also be attached to requests, yet the repeated area value does not become an independently measured attribute of each reporter. If the question concerns differences among places, the analysis should first aggregate to one row per area and state how many requests support each area summary. If the question concerns individual behavior or a causal effect of neighborhood conditions, the available merge does not supply the necessary individual measurements or design. The join therefore expands the set of descriptive questions that can be asked while leaving reporting coverage, geographic mismatch, and temporal alignment as explicit limitations.

6.6 Validate the Prepared Data

Validation compares the prepared table with the input and with the stated analytical contract. The following checks require the request count and identifier uniqueness to survive filtering, renaming, derivation, and the area merge. They also require the retained timestamps and problem label to remain within the intended scope and confirm that the closure field exists. The join report above separately records unmatched keys, so a passing row count does not conceal incomplete geographic coverage. These checks detect specific implementation errors, but they cannot prove that a source value is true or that the selected week represents a broader population. If the prepared table is saved for later use, its schema, source-to-analysis name mapping, join report, and relevant invariants should be stored with it and checked again after reading it back. A successful write operation alone does not establish semantic or numerical validity.

prepared = contextual_analysis.reset_index(drop=True)

final_checks = pd.Series({
    "same request count": len(prepared) == len(parking),
    "unique request identifiers": prepared["request_id"].is_unique,
    "all in intended week": prepared["created_at"].between(
        start, end, inclusive="left"
    ).all(),
    "all illegal parking": prepared["problem"].eq("Illegal Parking").all(),
    "closure field present": "closure_hours" in prepared.columns,
}, name="passed")

6.7 Preparation as a Documented Argument

The prepared table is a documented argument about which records and values can support the working question. Filters define scope, derived fields operationalize measurements, and the merge asserts a limited relationship between two geographic identifiers. The checks make those claims reviewable without implying that the source is error free. The exploratory and visualization chapters call a shared preparation function for the screened request fields and closure hours; that compact function does not reproduce this chapter’s full 44-column mapping, time-period category, or enriched context table. Those later chapters construct only the additional fields their questions require. This division keeps the transformation logic visible here while avoiding a second long import and renaming sequence in each chapter. It also identifies a reproducibility obligation: if the screening rule or closure-time definition changes, the shared function and the explanations in this chapter must be reviewed together.

Exercises

These exercises extend the import and checking work in the previous chapter. For the first exercise, begin with the screened table saved as data/illegal_parking.feather in that assignment. Do not repeat its import, scope filters, key checks, missingness report, or closure-time calculation. Keep the distributed ZIP archive unchanged, and include code with a concise explanation of each decision.

6.1 Prepare an analysis table that can support exploratory comparisons and a subsequent logistic-regression analysis.

  1. Inspect the observed values of Problem Detail and Status. Propose recoding only where the values support it. Show a mapping table, retain source values, and explain how unknown or rare values will be handled.
  2. Rename only the fields needed for your analysis using a consistent convention. Show the old-to-new mapping, check for name collisions, and leave the imported table unchanged.
  3. Merge data/zcta_context.csv using the documented ZIP-to-ZCTA match described in Section 6.5. Validate the merge cardinality, unmatched records, and preservation of one row per request. Explain why the match does not make ZIP Codes and ZCTAs equivalent.
  4. Write a concise data dictionary for the fields used, including source or derived status, units, and limitations. Propose a binary closure-time outcome that marks requests taking at least two hours to close, and explain whether this threshold suits your question. Identify candidate predictors available when a request is created. Keep post-creation fields out of that predictor list and explain why.

6.2 Construct and validate a request-level measure of straight-line distance to the nearest NYPD precinct station.

  1. Obtain a precinct roster from an authoritative source. Record the source, access date, precinct identifier, and address for each station. Explain why the precinct code in a 311 request identifies an administrative area but does not provide the station’s point location.
  2. Geocode the precinct addresses and retain the original address, returned coordinates, geocoding method, and any match-quality information. Review unsuccessful or ambiguous matches rather than assigning coordinates automatically. Save the reviewed geocodes with their provenance so that a later render does not repeat external geocoding requests.
  3. Check that station and request coordinates are present and plausible. Convert both sets of points to a suitable projected coordinate reference system before calculating distances. State the projection and units, and explain why distances calculated directly from longitude and latitude in degrees are not suitable.
  4. For each request with coordinates, find the nearest station and calculate the straight-line distance in a stated unit. Retain the nearest station’s identifier and the distance in the derived table. Report how many requests could not receive a distance and why.
  5. Compare the nearest station’s precinct identifier with the request’s Police Precinct value. Summarize matches and differences, and explain why distance to the nearest station and assignment to a precinct are distinct geographic measures.
  6. Validate that the distance calculation did not change the request count or duplicate Unique Key. Discuss why straight-line distance is not travel distance, response time, or evidence that proximity causes faster closure.

6.3 Write a preparation plan for a different question suggested by the data. This exercise concerns the table and its checks; the visualization proposal in Chapter 8 addresses figure design.

  1. State the question, intended audience, observational unit, outcome, and comparison. Specify whether the question is descriptive, comparative, predictive, or causal.
  2. List the fields and any additional data required. For each proposed transformation, state its purpose, expected row unit, and a check that could detect an error.
  3. Identify one issue that should be raised with a data curator rather than silently corrected. Draft a concise recommendation that distinguishes evidence from conjecture.
  4. Describe what the prepared table will contain, what it will omit, and how its provenance will let another analyst reproduce the result.
