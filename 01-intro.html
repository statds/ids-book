1  Introduction

1.1 What Is Data Science?

Data science is the practice of learning from data. It combines statistical reasoning, computation, and knowledge of the setting in which the data arose. None of these components is sufficient by itself. A technically sophisticated model can answer the wrong question; a sound statistical method can fail when implemented incorrectly; and efficient code cannot repair measurements that do not represent the phenomenon of interest.

Bin Yu’s \(SDC^3\) formulation captures this interdisciplinary breadth. In her 2014 presidential address to the Institute of Mathematical Statistics, she summarized the field as follows (Yu, 2014):

\[ \text{Data science} = S D C^3, \]

Yu’s formulation gives each component of data science a distinct role. Here, \(S\) is statistics, \(D\) is domain or scientific knowledge, and the three \(C\)s are computing, collaboration, and communication. Statistics provides ways to reason from observations while accounting for variation and uncertainty. Domain knowledge connects an analysis to a meaningful question and helps us judge whether its assumptions are sensible. Computing makes it possible to acquire, organize, explore, and model data at useful scales.

Collaboration and communication are not additions made after the technical work is complete. Data-science problems are commonly defined and solved by people with different forms of expertise. Their work becomes useful only when the question, evidence, assumptions, limitations, and conclusions can be understood by others. Data science is therefore both a technical and a social practice.

1.2 The Data-Science Workflow

A data-science workflow organizes a project into seven recurring activities:

  1. Formulate a question. Identify the decision or phenomenon of interest and determine what kind of answer is needed.
  2. Acquire and understand data. Learn how the observations were generated, what each variable measures, and which population they represent.
  3. Prepare the data. Correct structural problems, handle missing values, combine sources, and record every transformation.
  4. Explore. Use summaries and visualizations to discover patterns, check assumptions, and refine the question.
  5. Model or quantify. Apply methods appropriate to the question and the way the data were collected.
  6. Evaluate. Check statistical, computational, and contextual validity; investigate alternative explanations; and describe uncertainty.
  7. Communicate and act. Present the evidence and its limitations in a form that supports an informed decision.

These activities form a cycle rather than a one-way pipeline. Exploration may reveal a measurement problem, model checking may require different data, and discussion with a domain expert may change the original question. Reproducible records of the data, code, environment, and decisions make such revisions manageable and allow other people to inspect the work.

1.3 Goals of This Course

This course develops the foundations needed to carry out that workflow. By the end of the course, students should be able to:

  • translate a substantive problem into an answerable data-science question;
  • use Python to import, organize, explore, visualize, and model data;
  • explain the principles behind the methods they use and interpret their results in context;
  • distinguish descriptive, predictive, and causal claims;
  • evaluate data quality, model performance, uncertainty, and possible sources of bias;
  • use Git to maintain a transparent history of a project and collaborate with others;
  • use Quarto to combine prose, code, results, and citations in a reproducible report;
  • communicate findings clearly without overstating what the evidence supports; and
  • identify ethical concerns and take responsibility for analytical choices, including work performed with the assistance of AI.

The aim is not mastery of every available command or algorithm. Tools will change, and unfamiliar problems are unavoidable. The more durable goal is to learn how to select tools, investigate problems, verify results, and explain the reasoning that connects a question to a conclusion.

1.4 Computing Foundations

Data science takes place in a computing environment: an operating system, a file system, a command-line shell, a Python installation, project-specific packages, and an editor or notebook interface. These components affect one another. A program that works in one environment may fail in another because a file is in a different location, a package version has changed, or a command is interpreted by a different shell. Understanding the environment is part of reproducible analysis.

1.4.1 Operating Systems and Software

Linux, macOS, and Windows all support data-science work but manage software differently. Installation instructions must therefore be read with the operating system in mind. Linux distributions commonly use system package managers such as APT or DNF; Homebrew is a widely used third-party package manager on macOS; and Windows provides tools such as Windows Package Manager as well as the Windows Subsystem for Linux (WSL).

An operating-system package manager and a Python package manager solve different problems. The former installs software for the operating system; the latter installs Python libraries into a Python environment. Mixing their roles without understanding which interpreter or environment is active is a common source of installation errors. For course work, use the documented project environment instead of installing packages into an unspecified global Python installation.

1.4.2 Files, Paths, and Directories

A file system organizes files into directories, also called folders. File Explorer on Windows, Finder on macOS, and a command-line shell are different ways of viewing and working with the same file system. A file downloaded in a web browser is not stored “in the browser”: it is saved somewhere in the file system.

1.4.2.1 Finding Your Files

The home directory is the starting point for locating a user’s files. It contains familiar folders such as Desktop, Documents, and usually Downloads. A web browser normally saves a download in Downloads unless the user or browser chooses another location. To find a recent download:

  1. Open the browser’s downloads list and use Show in folder, or open Downloads in File Explorer or Finder.
  2. Check the file name and extension. A file called survey.csv is different from survey.csv.zip or survey (1).csv.
  3. Move course materials from Downloads into a deliberately named project folder. Do not let Downloads become the permanent organization for an analysis.
  4. If the download is a .zip archive, extract it and identify the new folder before trying to run or edit its contents.

From a Unix-like shell, ~ denotes the home directory. The following commands answer three basic questions:

pwd             # Where am I now?
ls              # What is here?
cd ~/Downloads  # Move to my Downloads folder.

The graphical and command-line views should lead to the same location. Run pwd again after cd and compare its output with the location shown in File Explorer or Finder. Software Carpentry provides a guided introduction to this navigation process (Software Carpentry, n.d.).

1.4.2.2 Absolute and Relative Paths

A path identifies a location in the file-system hierarchy. An absolute path starts at the file-system root and identifies a location without reference to the current working directory. Examples include /home/lee/air-quality/data/raw.csv on Linux and C:\Users\Lee\air-quality\data\raw.csv on Windows. Such a path is tied to a particular machine and user account.

A relative path is interpreted from the current working directory. If the working directory is the project folder air-quality, then data/raw.csv identifies the same file without recording where the project is stored. The special path . denotes the current directory and .. denotes its parent. Software Carpentry provides diagrams and exercises for learning how absolute and relative paths are resolved (Software Carpentry, n.d.).

For files within a project, prefer paths relative to the project root. If the whole project directory is moved to a different computer, every internal relative path can remain valid; absolute paths containing a user’s home directory generally cannot. This is why project-relative paths are important for portability and reproducibility. Keep each project in its own directory, separate source data from generated results, and run the analysis with a known project root (Wilson et al., 2017).

1.4.2.3 Naming Files and Folders

Good file and folder names are readable by people and predictable for software. Follow these conventions:

  • use short, descriptive names such as survey-responses.csv and clean-data.py;
  • use lowercase letters, digits, hyphens, and underscores, and avoid spaces and characters that have special meanings in a shell;
  • choose one delimiter convention and apply it consistently;
  • write dates in sortable YYYY-MM-DD order and zero-pad sequence numbers when ordering matters; and
  • use stable content-based names instead of names such as final-v2-revised; let version control record revisions.

The Windows directory C:\Program Files illustrates an unfortunate naming convention for command-line work. The space is legal, but a shell may interpret it as the boundary between two arguments unless the entire path is quoted, as in "C:\Program Files". Users must accommodate system paths they do not control, but should not copy this convention into data-science projects. Prefer air-quality to Air Quality Project. Software Carpentry gives the same recommendation because spaces and other shell-sensitive characters complicate commands, loops, and scripts (Software Carpentry, n.d.).

Portable file handling requires attention to case, extensions, and hidden files. Names may be case-sensitive on one operating system but not another, and extensions such as .csv, .py, and .qmd signal different kinds of content. Hidden files often store configuration.

Every file operation should begin with a check of its source and destination. Before reading or writing a file, know the current working directory, the intended path, and whether the operation will replace an existing file.

1.4.3 The Command Line

This book standardizes on Unix shell conventions for command-line work. Its basic commands work in Git Bash, Cygwin, WSL, macOS terminals, and Linux terminals. On Windows, use Git Bash, which is distributed with Git for Windows and provides a Bash emulation for running Git and Unix-style commands (Git for Windows, n.d.).

Do not use PowerShell for the command-line examples in this book. PowerShell defines familiar names such as ls, cp, and rm as aliases for PowerShell cmdlets rather than the corresponding Unix programs. The names may appear to work while their options and behavior differ (Microsoft, n.d.). In this course, use PowerShell only when a Windows-specific software installation step explicitly requires it.

The following shell commands form a useful starting vocabulary:

  • pwd prints the current working directory;
  • ls lists directory contents;
  • cd changes the current directory, with .. denoting its parent;
  • mkdir creates a directory;
  • cp copies files or directories;
  • mv moves or renames files or directories; and
  • rm removes files.

Options modify the behavior of a command. For example, ls -a includes hidden entries and ls -l displays additional details. Consult a command’s documentation before using unfamiliar options. Use tab completion while typing commands and paths: it completes valid names, reveals what is available, speeds up repetitive work, and reduces errors caused by misspelling or misquoting a file name.

Commands that overwrite or remove data require special care. Check every path before running them; command-line deletion may not use a desktop trash folder.

A short command list is only a starting point for shell fluency. The Software Carpentry lesson The Unix Shell provides a fuller introduction to navigating and modifying files, combining commands with pipes, automating repetition with loops, and writing shell scripts (Software Carpentry, n.d.).

1.4.4 Python and Its Environment

Python is the primary programming language used in this book. A working setup requires a supported Python 3 interpreter, an isolated environment containing the required packages, and an interface for editing and running code. The interface may be a notebook, an editor, or an integrated development environment; the underlying project should remain reproducible regardless of which interface is used.

Readable code is easier to verify, revise, and share. Python’s principal style guide is PEP 8 (Van Rossum et al., 2001). For a start, follow three conventions:

  • use four spaces for each indentation level and do not mix tabs and spaces;
  • give variables and functions descriptive lower_case_with_underscores names; and
  • use whitespace consistently, keep statements on separate lines, and wrap long lines inside parentheses when they become difficult to read.

Consistent style makes analytical code easier to inspect and trust. Clear code exposes assumptions and makes errors easier to find, but consistency within a project matters more than mechanically applying a rule that reduces readability.

Two freely available books provide broader instruction in the Python data-science ecosystem. The Python Data Science Handbook (VanderPlas, 2016) covers NumPy, pandas, visualization, and machine learning, while Python for Data Analysis (McKinney, 2022) develops data manipulation with pandas in greater depth.

1.5 Tools for Reproducible Data Science

Coursework should produce artifacts that remain useful after the semester ends. When an assignment is written in Quarto, its clear prose, executable analysis, figures, citations, and reproducible source can be revised into a research memo, portfolio sample, lab report, or presentation for another audience. Students should therefore treat homework as practice for professional communication, not as a disposable file submitted only for a grade; attractive output is valuable because it helps readers understand trustworthy work, not because appearance can substitute for sound reasoning (Quarto Developers, 2025).

1.5.1 Installing Quarto

Quarto is the publishing tool used throughout this book, so install it before you try to render a .qmd file. Follow the official Quarto installation guide for your operating system, then verify the installation from Git Bash, WSL, macOS Terminal, or a Linux shell:

quarto --version
quarto check

The quarto command must be available on your PATH. If the shell reports command not found, finish the installation or reopen the shell so it reloads the updated PATH. Chapter 3 combines Quarto with Python and Jupyter to produce executable documents (Quarto Developers, 2025).

You can test the installation with a minimal document before working on the book. Create hello.qmd with the following contents:

---
title: "Hello, Quarto"
format: html
---

# A Short Introduction

This document was rendered by **Quarto**.

## What I Am Learning

I am practicing Markdown before adding executable analysis.

- headings organize a document;
- emphasis draws attention to important words; and
- links connect the document to [Quarto's guide](https://quarto.org/docs/guide/).

From the directory containing the file, run:

quarto render hello.qmd

Quarto should create hello.html. Open that file in a browser and check that the title and sentence appear. The source file is the record of what you wrote; the HTML file is generated output and should not replace the source.

1.5.2 Installing Git

Git is the version-control tool used throughout this book, so install it before you begin the collaboration exercises. Follow the official Git installation instructions, or install Git for Windows and use Git Bash on Windows. Verify the installation and identity from your shell:

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --list --show-origin

Chapter 2 explains repositories, commits, branches, remotes, and pull requests. Chapter 1 only asks you to install and verify Git; do not install project packages globally.

1.6 Responsible Practice

Ethical questions occur throughout a project, not only when results are published. Data may have been collected without meaningful consent, omit groups affected by a decision, encode historical inequities, or reveal private information when combined with other sources. A model may distribute errors unevenly, and a technically correct analysis may still be used for a harmful or unjustified purpose.

Responsible practice begins by asking who created the data, who is represented, who is missing, who benefits from the analysis, and who bears the risks. Collect and retain only what is needed; protect sensitive information; document provenance and transformations; examine performance across relevant groups; and communicate limitations. Legal compliance is necessary in regulated settings, but it is not a substitute for ethical judgment.

Accountability remains with the people conducting and deploying an analysis. This is especially important when AI generates code, models, or prose. The apparent fluency of an output is not evidence that the data were appropriate, the computation was correct, or the conclusion was justified. Every result must be examined with the same statistical, computational, contextual, and ethical scrutiny regardless of how it was produced.

1.7 Communicating Data Science

An analysis has little value if its audience cannot understand what was learned or decide how to respond. Effective communication begins with the question and the main finding, then supplies the evidence needed to support that finding. Tables and graphics should have a clear purpose, informative labels, honest scales, and enough context to be interpreted without guesswork.

Good communication also makes uncertainty and limitations visible. Report what the data cover, distinguish observed patterns from explanations, and avoid causal language when the design supports only association. Provide enough information about data sources, software, and analytical choices for others to inspect or reproduce the work. The objective is not to make a result sound certain; it is to make the reasoning transparent and useful.

Exercises

Write one .qmd file containing your answers to all problems.

  1. Prepare your computer for this course.
    1. Install Git and Quarto, record your operating system and the outputs of git --version, quarto --version, and quarto check, and configure and verify your Git identity.
    2. Explain one installation problem and its solution.
    3. State which commands you used to verify both installations.
  2. Find and describe a file without relying on a graphical application’s recent- files list.
    1. Use pwd, ls, and cd to locate your home directory and Downloads.
    2. Describe that folder with both an absolute path and a path relative to your project directory, and explain why the relative path is more portable.
    3. Explain why the relative path is preferable when the project is moved to another computer.
  3. Establish naming and organization conventions for a new project.
    1. Create a practice directory containing three files with recommended names and one deliberately difficult name.
    2. Explain why the difficult name causes trouble in a shell, rename it, and show the commands and directory listing.
    3. Why do professionals use the command line for project work?
    4. Why do Linux and Windows organize software differently?
    5. Why should source files be separated from generated or binary files?
    6. Give one collaboration problem caused by spaces in names, lines longer than 80 characters, or untracked output.
