3  Reproducible Data Science

Quarto turns plain-text source into reproducible documents that combine explanation, computation, results, figures, and references. A data-science analysis should be reproducible because readers need to inspect how evidence was produced, not merely see a final picture or a pasted table. Quarto supports Python, R, Julia, and Observable and can publish articles, reports, websites, books, and presentations in several output formats (Quarto Developers, 2025b).

This chapter is a jump start, not a replacement for the complete Quarto Guide. Use the guide when you need options not covered here, and consult the Python documentation, Markdown reference, and presentation documentation for detailed examples (Quarto Developers, 2025d, 2025a, 2025c).

3.1 A Minimal Quarto Document

A Quarto document is a text file whose .qmd extension combines YAML metadata, Markdown prose, equations, citations, and executable code chunks. The following small document is a better starting point than a code-only hello-world: it produces a numerical result, a table, and a figure from the same code that explains them.

Create a file named hello.qmd with YAML metadata like this:

---
title: "Hello, Quarto"
author: "Your Name"
format: html
jupyter: python3
bibliography: references.bib
---

The document can then combine prose, equations, and executable code. Equation punctuation follows ordinary sentence punctuation. The mean of observations \(x_1,\ldots,x_n\) is given by Equation 3.1.

The source syntax for this numbered equation is:

The mean ... is given by @eq-mean.

$$
\bar{x} = \frac{1}{n}\sum_{i=1}^{n} x_i.
$$ {#eq-mean}

\[ \bar{x} = \frac{1}{n}\sum_{i=1}^{n} x_i. \tag{3.1}\]

A cases display can continue a sentence with a comma, as shown in Equation 3.2:

\[ g(x) = \begin{cases} 0, & x < 0,\\ 1, & x \ge 0. \end{cases} \tag{3.2}\]

The comma after the first case and the period after the final case are part of one grammatical statement. The code below generates a table and a figure from the same observations:

import matplotlib.pyplot as plt
import pandas as pd
from matplotlib_inline.backend_inline import set_matplotlib_formats

set_matplotlib_formats("svg")

scores = pd.DataFrame({"student": ["A", "B", "C"],
                       "score": [82, 91, 87]})
scores["score"].mean()
scores

fig, ax = plt.subplots()
ax.bar(scores["student"], scores["score"])
ax.set(xlabel="Student", ylabel="Score", title="Scores")
plt.show()

The resulting table and Figure Figure 3.1 summarize the observations above. Quarto itself is documented in the Quarto Guide (Quarto Developers, 2025b).

The opening and closing lines between --- define YAML metadata. Headings use one or more # characters, ordinary text forms paragraphs, dollar signs mark LaTeX equations, and a fenced code chunk begins with ```{python}. The jupyter: python3 setting tells Quarto which Jupyter kernel should execute Python chunks. Expressions whose values are displayed, such as scores, and figures returned by the chunk become part of the rendered document.

Render the document from its directory:

quarto render hello.qmd

Quarto writes hello.html by default. Open that file in a browser, or use quarto preview hello.qmd while editing to render again after each save. Keep the .qmd source under version control; treat the rendered HTML as generated output.

3.2 Markdown Essentials

Markdown provides the readable structure around an analysis. The following constructs cover the structures needed in early assignments:

# Chapter title
## Section heading

**bold**, *italic*, and [a link](https://quarto.org/)

- an unordered list
- another item

1. a numbered step
2. another step

`inline code` and a code block:

```python
print("This block is displayed, not executed by Quarto.")
```

> A block quote highlights a definition or key point.

| quantity | value |
|:--|--:|
| observations | 3 |
| mean | 86.7 |

![A descriptive caption](figures/scores.png)

See the Quarto Guide [@quarto2025guide] and @eq-mean.

Use a heading hierarchy rather than bold text to organize a document. Put a blank line around paragraphs and lists, write descriptive link text, and keep code that should execute in a Quarto code chunk. Use a meaningful caption for each figure and cite sources near the claim they support. The Markdown basics reference covers tables, images, citations, cross-references, callouts, and other features.

3.3 Why the Software Environment Matters

An analysis is a combination of source code and the software environment that interprets it. Two computers can run the same source and obtain different results when they use different Python versions, package versions, operating- system libraries, or default settings. A result that cannot be rerun after an environment changes is not fully reproducible, even when the code is available (Wilson et al., 2017).

An isolated environment makes these dependencies explicit and prevents one project from silently changing another. Recording the Python version and the installed packages lets a collaborator recreate the computational setting, while a lockfile or pinned requirements file records the versions tested here. This practice also makes failures diagnosable: when an upgrade changes an output, we can identify the change instead of guessing which global installation caused it.

3.4 Python Environments for Quarto

Quarto executes Python through a Jupyter kernel, so the interpreter and packages must be installed in an environment that Quarto can find. A virtual environment keeps this project’s packages separate from the system Python and from unrelated projects.

This repository uses Python 3.12 as its tested compatibility target. The recommended local environment is .ids, created and managed with uv. uv is a fast command-line tool for installing Python versions, creating virtual environments, and installing packages; it is not a replacement for Python or Quarto. Students who prefer the standard Python tools can use the pip alternative below.

uv venv --python 3.12 .ids
source .ids/bin/activate
uv pip install jupyter matplotlib pandas

The environment name is a convenience, not a requirement. Students may use a different name, such as .venv, provided that Quarto and the editor use that environment’s Python kernel. When the name differs from the Makefile default, pass the chosen name explicitly:

make req VENV=.venv
make render VENV=.venv

The first command records installed packages in requirements.txt; the second renders the book. Do not install packages into the system Python, and do not commit the virtual-environment directory. Keep the environment specification and the source files under version control instead.

If uv is not available, create the environment with the standard library and install the same packages with pip:

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install jupyter matplotlib pandas

Use python --version, which python, and jupyter kernelspec list to verify that the active interpreter is the one you intend to use. If Quarto reports that it cannot find a kernel, select the environment’s Python interpreter in your editor or install its kernel with python -m ipykernel install --user.

3.5 Reproducibility in Practice

Reproducibility requires a record of the inputs, environment, instructions, and decisions that produced an analysis. A Quarto file brings prose and executable code together, but it cannot by itself make an undocumented dataset, unrecorded random seed, or unavailable package reproducible.

For each analysis, preserve these five components:

  1. Source: the .qmd file and any scripts it calls.
  2. Data: the source, version, download date, and transformations for each dataset; keep private or large raw data outside Git when necessary.
  3. Environment: the Python version, package requirements, Quarto version, and operating-system details needed to run the source.
  4. Execution: the commands, options, random seeds, and order of steps used to render the document.
  5. Outputs: tables, figures, and conclusions checked against the source, not manually edited after rendering.

Use relative project paths, pin important package versions, set random seeds when simulation is involved, and render from a clean working tree. These habits make it possible for another analyst to inspect and repeat the work (Wilson et al., 2017).

3.6 Rendering the Book

Rendering checks whether the source, computations, citations, and cross- references work together. From the repository root, use the Makefile targets:

make check
make render
make preview

make check verifies the command-line tools, make render builds the complete book in _book/, and make preview starts a local server with live reload. For a quick test of one source file, use:

make render-one FILE=hello.qmd

Read the terminal output rather than assuming a successful command produced a correct document. Check that code results make sense, links work, figures have captions, citations resolve, and the output contains no accidental secrets or local file paths. Generated _book/, .quarto/, and cache files belong in .gitignore, not in a commit.

3.7 Presentations with Quarto

Quarto presentations should replace the default habit of preparing course work in a proprietary PowerPoint file. A presentation remains plain text, versionable, reproducible, and reviewable while still producing a polished slide deck. Quarto supports reveal.js slides in HTML and can also produce other formats; the presentation guide explains the available options.

A well-made Quarto homework is a reusable professional artifact, not a disposable submission. The same source can become a polished report, research memo, lab note, portfolio piece, or presentation for a different audience by changing its format and explanation while retaining the executable analysis. Students should therefore treat each assignment as an opportunity to practice communicating evidence to people outside this course: clear prose, labeled figures, citations, and a reproducible source record are more valuable than a decorative layout alone (Quarto Developers, 2025b).

Excel, Word, and PowerPoint are useful office tools for administrative staff, but they are not data-science authoring tools. Students should not author data-science assignments in these MS Office formats: their binary contents produce opaque diffs, make line-by-line review difficult, and can preserve hidden formatting or manually edited results without recording how those results were computed. Use a .qmd file, code, data description, and environment as the authoritative record; an HTML rendering is the normal output, and a PDF may be exported only when an audience or assignment specifically requires it. The reason is methodological: a data-science submission must expose executable transformations, preserve data and software provenance, support line-by-line review, and reproduce the same outputs after the source changes. Office files primarily preserve a presentation or a spreadsheet state; they do not reliably preserve that computational record (Wilson et al., 2017).

Plain-text source and Git also provide benefits that office workflows lack. Version history records who changed which lines and makes earlier versions recoverable, rather than hiding revisions in a track-changes pane or a file named final-v2-revised. Code automates repeated calculations, keeps tables and figures synchronized with the data, and can be tested after each change. Several people can review, merge, and reuse the same source without passing around conflicting binary attachments.

Create a presentation by choosing a presentation format in the YAML header:

---
title: "A Data-Science Result"
format: revealjs
---

## The question

What decision does this analysis support?

## The evidence

Explain the important figure and its limitations.

Render it with quarto render presentation.qmd or preview it with quarto preview presentation.qmd. Use headings for slides, keep one central idea on each slide, and write speaker notes when additional explanation belongs in the oral presentation rather than on the slide. Export a PDF only when a course or audience requires a static copy; keep the .qmd source as the authoritative presentation.

Exercises

Complete the Git setup from Chapter 2 and the Quarto installation from Chapter 1 before beginning. Document each exercise in a .qmd file as a user manual for another beginner:

  1. Build and inspect a reproducible Quarto document.
    1. Record your operating system, Python version, Quarto version, and any installation obstacle; explain how you verified that Quarto can find the Python environment.
    2. Create the environment, open the project in your editor, and reproduce the polar-axis line plot from the Quarto presentation guide with a caption.
    3. Add prose, an equation, an executable Python chunk, and a generated figure to a short document; render it to HTML, inspect it in a browser, and correct warnings or unresolved references.
  2. Publish and preserve the work.
    1. Render the homework to PDF and place the PDF in a GitHub release, while keeping the .qmd source under version control and excluding the virtual environment and generated _book/ output.
    2. Commit in small, meaningful steps and push the branch to your fork.
    3. Include the HTML link, release link, commands, and troubleshooting notes in the homework so another student can reproduce the result.
